## 一句话

**Secure Agent Workspace（安全 Agent 工作区）**：给企业自主运行的 AI Agent 一个**受治理的执行场所**——用户端点只负责展示，真正的执行发生在受管理的远程工作区里，身份、网络、凭据、运行时策略、审计、人工审查共同约束 Agent 能做什么。

---

## 背景：为什么需要它

企业正从「聊天式助手」转向 **always-on 个人 Agent**——它能读代码、查文档、跑测试、查询系统，连续运行数小时。

这个转变带来新的平台需求：**需要一个安全、受管理的 Agent 执行环境**（不能只靠提示词约束）。

```
用户端点（浏览器/终端/IDE）= 展示层，不是执行层
Agent 运行时 = 受管理的远程环境（单用户 VM，可选 GPU 加速）
   ├─ 经审批的生命周期供给
   ├─ 经可信代理访问
   ├─ 被运行时强制层约束
   └─ 经受治理的连接器接入企业系统（敏感写入需人工审查）
```

---

## 🛡️ 防护对象（Protecting Against）

| 威胁 | 说明 |
|:-----|:-----|
| **未授权/意外写入** | Agent 改错工单、删错文件、跑破坏性命令（人为失误或指令劫持）而无人审查 |
| **数据外泄** | 被劫持或越权的 Agent 把私有数据发给未列明地址（出站流量或写入夹带） |
| **提示注入** | 藏在文档、邮件、工单、上游工具输出里的指令劫持 Agent——即使原始用户提示词是合法的 |
| **Agent 作为攻击者（出站滥用）** | 扫描/利用内部服务、对内外系统 DoS、横向移动、经连接器发恶意流量 |
| **VM 内 root 沦陷** | 内核 CVE 或本地提权发生在工作区 VM 内，但 VM 边界防止波及用户主机 |

## 🏗️ 参考架构：七个逻辑平面

**端点只是用户界面（IDE/终端/编码 Agent），受管理工作区才是执行与策略边界。**

```
Plane 1-4（外围）: 端点、身份、访问代理、生命周期治理
Plane 5-7（执行）: 网络边界、运行时沙箱、工作区 VM / 观测
```

（详见官方 Figure 5：seven logical planes）

### 从内到外的包含关系

```
Agent 循环 → 运行时沙箱 → 单用户工作区 VM → Secure Agent Workspace 外壳
```

### 架构不变量（Architectural Invariants）

| 不变量 | 强制位置 | 机制 |
|:-------|:---------|:-----|
| **原始凭据不进 Agent** | 运行时沙箱（Plane 6） | 凭据代理在出口重写 Authorization 头；Agent 拿到的是「能力」而非「密钥」 |
| **无自我授权** | 沙箱 + 控制面 | Agent 只能以用户权限的策略定义子集运行，不能扩大自身范围（需控制面重签委托） |
| **不连未列明地址** | 网络边界 + 沙箱出口（双重防御） | 双重 deny-by-default；出站目标来自签名白名单 |
| **不篡改系统二进制** | 运行时沙箱 | 可写目录之外只读；支持的内核上用 LSM 强制 |
| **无 Agent 创建的持久化** | 运行时沙箱 | `.bashrc`、shell 钩子、MCP 配置 deny-write（否则每次会话都会执行，与提示词无关） |
| **无 Agent 控制的生命周期** | 控制面（运维持有） | 沙箱创建、策略变更、镜像升级都是运维操作 |
| **无被抑制的审计** | 信任边界端点 | OCSF 遥测从 VM 外周边和 VM 内运行时发出，Agent 进程无法禁用/篡改 |

## 🎯 关键组件

| 组件 | 说明 |
|:-----|:-----|
| **工作区环境** | 受管理的 Linux/Windows 工作站、VM 或 GPU 加速工作站 |
| **生命周期 Portal/API** | 唯一的权威控制面：创建/启动/停止/暴露/连接/退役 |
| **接入模式** | 终端、IDE、应用、GUI 四种接入；持久用户状态 |
| **运行时约束层** | 沙箱 + 策略引擎 + 凭据代理 + 路由推理 + deny-by-default 出口（参考实现：**NVIDIA OpenShell**） |
| **可信访问代理** | 企业 SSO 支撑，签发有界、可审计、短时会话 |
| **分层身份面** | 用户/赞助人（SSO）→ 工作区（设备身份）→ Agent（逻辑注册）→ 每次工具调用（短时凭据），全部可追溯 |
| **逐任务委托记录** | 签名委托记录绑定四层身份与有界权限（任务、资源、工具、时长、审批、吊销、审计）；子代理只能收窄父代理范围 |
| **Agent 治理层** | 签名策略编写分发、舰队遥测、审计、人工审查门 |
| **企业系统受治理接入** | Git、工单、文档、聊天、邮箱、包仓库、数据存储、模型端点 |

## 📈 成熟度模型（Phase 0 / I / II）

| 阶段 | VM 内 | VM 外 |
|:-----|:------|:------|
| **Phase 0（基线）** | 配置管理、补丁、EDR、镜像治理、SOC 遥测 | —（企业托管 VM 标配，必要但不充分） |
| **Phase I：Agent 在受管理 VM** | 编码/知识 Agent 跑在单用户托管工作区 + 企业镜像 + EDR | SSO + 访问代理、镜像治理、网络边界白名单、写入人工审查、工作区边缘审计 |
| **Phase II：签名策略强制的运行时沙箱** | Phase I + 运行时沙箱（OpenShell 或等价）在工具调用边界强制签名策略包：deny-by-default 出口、凭据代理、路由推理、文件系统/进程限定 | Phase I + 集中签名策略编写/分发/证明链（启动时证明、每次调用验证） |

- Phase I 是**今天就能部署**的基础；Phase II 增加运行时强制层，**遏制 VM 内 OS 沦陷的爆炸半径**
- 阶段是**叠加**的：Phase II 不替代 Phase I

## 🔗 与前沿知识库其他条目的关联

- **learn-claude-code**：讲的是 Harness 的「功能机制」（loop、工具、权限、团队）——Secure Agent Workspace 是它的**企业安全落地形态**（身份、凭据代理、签名策略、审计）
- **AF/PD 分离**：讲推理侧的部署架构——Secure Agent Workspace 讲**Agent 执行侧**的部署架构
- **对「多智能体平台」项目**：子代理委托记录（只能收窄不能扩大）、逐任务签名授权、凭据代理不落 Agent 进程——都是可直接借鉴的生产级安全设计

## 📌 小结

- **核心思想**：Agent 自主行为应由**环境**约束，而非仅靠提示词约束（runtime-bounded，prompt-independent）
- **三句话记住**：端点只展示不执行；凭据只给能力不给密钥；策略由控制面签发、由运行时强制、不可被 Agent 绕过
- 参考实现：NVIDIA OpenShell（运行时沙箱）、NemoClaw（agent harness）、NeMo Agent Toolkit（技能与观测）

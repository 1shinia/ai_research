# 🔍 背景调研：为什么需要智能路由

> **状态**：🔵 调研中 · **进度**：0%

## 核心痛点

### 1. 模型选择困境

现在可用的模型越来越多，每个场景选哪个成了难题：

| 问题 | 说明 |
|:----|:------|
| **大材小用** | 简单翻译、摘要也调用最强模型，成本浪费 10-100 倍 |
| **小材大用** | 复杂推理任务用了小模型，输出质量不达标 |
| **选择疲劳** | 几十个模型各有优缺点，人工决策不现实 |
| **动态变化** | 模型价格、性能、可用性在持续变化 |

### 2. 成本爆炸

- GPT-4 vs GPT-4o mini：价格差 **30-60 倍**
- 如果所有请求都用最强模型，月均 API 费用可能高数万元
- 实际场景中 60-80% 的请求其实不需要最强模型

### 3. 延迟不均衡

- 小模型响应 < 1s，大模型可能 5-30s
- 用户对简单查询的期望是毫秒级响应
- 不能一刀切用统一模型

### 1. 模型能力评估矩阵

**目标**：建立可量化的模型能力画像，支撑路由决策。

| 维度 | 指标 | 数据来源 |
|:-----|:-----|:---------|
| 推理质量 | MMLU / HumanEval / GSM8K / MT-Bench 分数 | 公开排行榜、厂商 spec |
| 推理速度 | TTFT / TPOT / 吞吐（tokens/s） | 压测、生产监控 |
| 成本 | 每千 tokens 价格（输入/输出） | 厂商定价页 |
| 上下文长度 | 最大支持 token 数 | 厂商 spec |
| 工具调用 | Function Calling 成功率、JSON 格式遵循率 | 自建评测集 |
| 多语言 | 中文/英文任务准确率 | 自建评测集 |
| 稳定性 | 可用性、错误率、限流阈值 | 生产监控 |

**落地形态**：`config/models.yaml` 中每个模型条目包含上述维度评分，路由时按任务类型加权计算匹配度。

---

### 2. 任务复杂度分类体系

**目标**：把用户请求自动归入 S/M/L/XL 四档，选择"最便宜够用"的模型。

| 档位 | 典型任务 | 特征信号 |
|:-----|:---------|:---------|
| **S（轻量级）** | 闲聊、简单翻译、格式转换、单步问答 | token < 200、无工具调用、无代码块、低置信度要求 |
| **M（中档）** | 多步推理、文档摘要、代码审查、中等复杂度问答 | token 200-2000、单工具调用、少量代码、需要思维链 |
| **L（重量级）** | 复杂分析、长文档处理、多工具编排、代码生成 | token 2000-8000、多工具、长代码块、高精度要求 |
| **XL（旗舰级）** | 深度研究、复杂数学证明、大规模代码重构、多轮 Agent 协作 | token > 8000、多轮 ReAct、需要强推理链 |

**动态调整**：实际路由时结合 flag_rules（high_risk/debug/strict_format 等强制升级）和 sticky 机制（多轮对话保持档位）。

---

### 3. 路由决策延迟预算

**目标**：路由本身不能成为瓶颈，决策延迟控制在毫秒级。

| 阶段 | 延迟预算 | 优化手段 |
|:-----|:---------|:---------|
| 特征提取 | < 1ms | 规则匹配、轻量正则、缓存上下文长度 |
| 复杂度评估 | < 1ms | 预计算 token 数、规则引擎 |
| Flag 分类 | < 0.5ms | 正则预编译、关键词哈希 |
| 档位决策 | < 0.5ms | 确定性规则、无 ML 推理（纯规则模式） |
| 模型选择 | < 1ms | 配置驱动、内存索引 |
| **总计** | **< 5ms** | 全流程内存操作、无 I/O |

**兜底**：若特征提取超时，直接按历史默认档位路由，不阻塞请求。

---

### 4. Fallback 策略

**目标**：路由错误或模型故障时，优雅降级保证可用性。

| 触发条件 | Fallback 动作 |
|:---------|:-------------|
| 模型超时（> 30s） | 降一档重试，最多 2 次 |
| 模型返回 5xx/限流 | 切换到同档备用模型池 |
| 输出格式校验失败 | 降档 + 注入严格格式提示词重试 |
| 工具调用连续失败 | 降档 + 简化工具集重试 |
| 路由决策本身异常 | 直接 fallback 到默认轻量级模型（如 glm-flash） |

**熔断机制**：连续 3 次失败后，该模型进入 60s 冷却期，期间不分配新请求。

---

### 5. 动态模型发现

**目标**：新模型上线后自动加入路由池，无需重启服务。

| 机制 | 实现方式 |
|:-----|:---------|
| 模型注册 | `models.yaml` 热加载 + inotify/watchdog 文件变更监听 |
| 健康检查 | 每 60s ping 一次 `/v1/models`，记录延迟/可用性 |
| 能力标签 | 模型元数据包含 `max_context`、`supports_tools`、`cost_per_1k` 等标签 |
| 自动路由 | 新模型加入后，按能力标签自动匹配适合的任务类型 |
| 灰度上线 | 新模型先以 `shadow` 模式运行（只记录不实际调用），验证稳定后切 `active` |

**配置驱动**：所有模型元数据集中在 `config/models.yaml`，服务启动时加载，运行时可热重载。
